# Kupala Hub: аналоги и доступность данных

Уточнение от 16.11.2026: расширенный [каталог данных других приложений](grsu-data-catalog.md) дополняет этот аудит. По публичным снимкам MyGRSU подтверждены профиль, типы групп и наличие пунктов оплаты, платежей и приказов. Детали закрытых ответов и доступ для Kupala Hub остаются неподтверждёнными. Текущая проверка портала приостановлена по решению пользователя.

Проверка: 15.11.2026. Область: десктопное веб-приложение, сервер на JavaScript. Основания: исходное ТЗ `reference/requirements.md`, спецификация, сохранённые экраны Claude, выбранный A и новые макеты расписания, задач и ассистента.

## Вывод

Рабочее ядро «Сегодня / Расписание / личные задачи / ассистент по этим данным» обеспечивается публичным API и собственными данными приложения. Весь первоначальный замысел с автоматической загрузкой оценок, пропусков, финансов и учебных материалов пока НЕ обеспечен подтверждёнными интеграциями. Демо не считается подтверждением доступности источника.

Это проверка выборки ответов и исходников, не доказательство полноты расписания всего университета, круглосуточной доступности или исчерпывающего перечня API. Приложения из магазинов не устанавливались; закрытые аккаунты не использовались. Их возможности изучены по описаниям разработчиков. Код открытого клиента просмотрен непосредственно.

## Непосредственная проверка публичного API

Все шесть методов ниже вернули HTTP 200 и JSON без университетского аккаунта. Проверялись небольшими последовательными запросами через виртуальный Playwright. Массовый обход групп не выполнялся.

База: `https://api.grsu.by/1.x/app1/`.

| Метод и параметры проверки | Наблюдаемый результат |
| --- | --- |
| [getFaculties](https://api.grsu.by/1.x/app1/getFaculties) | 16 элементов `items`, поля `id`, `title`; среди них также учреждение, институт и центр — не называть все 16 строго факультетами |
| [getDepartments](https://api.grsu.by/1.x/app1/getDepartments) | 5 форм: дневная, заочная, вечерняя, дистанционная, соискательство. Это не кафедры |
| [getGroups](https://api.grsu.by/1.x/app1/getGroups?departmentId=2&facultyId=3&course=2) | 13 групп в выбранном срезе ФМИ, дневная форма, 2 курс; `id`, `title`. Это не общее число групп университета |
| [getTeachers](https://api.grsu.by/1.x/app1/getTeachers?extended=true) | 1106 записей; `id`, `name`, `surname`, `patronym`, `post`, `phone`, `descr`, `email`, `skype`. Контакты часто пустые, есть отрицательные ID; нельзя требовать положительный ID или наличие email. Это число записей, не подтверждённое число действующих сотрудников |
| [getGroupSchedule: ФМИ](https://api.grsu.by/1.x/app1/getGroupSchedule?groupId=18159&dateStart=16.11.2026&dateEnd=22.11.2026) | 6 дней / 31 запись занятия. Есть суббота и одновременные занятия разных подгрупп. Это не 31 обязательная пара конкретного студента |
| [getTeacherSchedule](https://api.grsu.by/1.x/app1/getTeacherSchedule?teacherId=14580&dateStart=16.11.2026&dateEnd=22.11.2026) | Один день с защитой курсовой; у занятия есть `id`, время, тип, предмет, адрес, аудитория, массив групп с формой/факультетом/курсом |

Дополнительные наблюдения:

- [Группа 15914 за 16–22 ноября](https://api.grsu.by/1.x/app1/getGroupSchedule?groupId=15914&dateStart=16.11.2026&dateEnd=22.11.2026): 6 дней, 32 записи; есть `Зачет (в устной форме)`, `Экзамен (в устной форме)`, `конс.`, `Курсовая работа (защита)`, `Контрольная работа`. Таким образом, события сессии действительно доступны в обычном расписании. Полнота для всех групп не проверена.
- Группа 18917 за ту же неделю вернула `count:0, days:[]`. Пустой ответ не подтверждает выходной: возможны неопубликованный период или особенности группы.
- В ответе группы: `date`, `num`, `lessons`, `timeStart`, `timeEnd`, `title`, `type`, `teacher.{id,fullname,post}`, `address`, `room`, `label`, `subgroup.{id,title}`. Даты запроса `dd.MM.yyyy`, ответа `yyyy-MM-dd`.
- В выборке группы у занятия нет стабильного `id`, тогда как в расписании преподавателя он есть. Алгоритм изменений должен учитывать это; нельзя безусловно связывать записи по ID.
- Реальные окончания пар — например 09:55 и 11:30; нельзя использовать выдуманную сетку 09:50/11:25 из макета.
- Значения `type` и `post` бывают пустыми, `room` может быть `-`; преподавателем может оказаться длинная строка комиссии. Нужны состояния «не указано», перенос текста и раскрытие подробностей.
- `getStudent(login)` найден в открытом клиенте, но не вызывался: логин пользователя не предоставлен. Этот метод нельзя считать входом в аккаунт.
- Полного официального каталога методов, SLA, лимитов, гарантированного горизонта публикации и готовой истории изменений в проверке не установлено. Ограничение 2 запроса/с в нашей спецификации — собственная настройка, а не опубликованный лимит ГрГУ.

## Матрица запланированных функций

«Да» ниже означает наличие источника или реализуемую собственную функцию; подключённого рабочего приложения пока нет.

| Функция / окно | Откуда брать | Решение и пределы |
| --- | --- | --- |
| Выбор группы и избранное | 3 публичных справочника + свои настройки | Да. Логин портала для этого не нужен |
| Сегодня, текущая/следующая пара | Расписание + время Europe/Minsk + выбранные подгруппы | Да. Не суммировать параллельные подгруппы как обязательные занятия |
| Неделя, день, месяц; карточка пары | getGroupSchedule | Да, в пределах опубликованных дат, включая выходные. Не фиксировать время звонков вручную |
| Фильтр подгруппы и языка | subgroup и названия занятий + выбор пользователя | Подгруппы подтверждены; отдельное структурированное поле иностранного языка не подтверждено |
| Экзамены, зачёты, консультации и отсчёт | type/date/time расписания | Да, если опубликованы. Это календарь событий, без допуска и результата сдачи |

| Офлайн, ICS, ссылка на расписание, печать | Наш кэш и генерация представлений | Да. Показывать дату снимка. Доставка push зависит от разрешения и среды браузера |

| Черновик письма преподавателю | Контакт, введённый текст, модель | Да при наличии email. Автоматическая отправка — отдельное действие, не следствие генерации |
| Корпуса и внешний маршрут | Адрес из расписания + проверенный справочник координат / сервис карт | Частично. Координат, этажей и времени пешком в проверенных ответах нет |

| Объяснение темы, поиск по файлам, учебный тест | Загруженные пользователем/доступные материалы + модель | Реализуемо. Нужны сами материалы; качество ответов и стоимость требуют отдельной проверки |

## Портал: что удалось подтвердить

1. GET `https://edu.grsu.by/login/index.php` привёл к форме единого входа ГрГУ. В форме видны SimpleSAML и SAML2, поставщик входа `idp.grsu.by`, сервис Moodle `edu.grsu.by/auth/saml2/sp/metadata.php`. Авторизация не выполнялась; параметры сессии и cookies не сохранялись в проект.
2. GET [Moodle REST без токена](https://edu.grsu.by/webservice/rest/server.php?moodlewsrestformat=json) вернул HTTP 200 с JSON `exception:moodle_exception`, `errorcode:invalidtoken`, сообщением о недействительном ключе. Это подтверждает наличие обработчика, но НЕ выдачу токена студенту, доступность конкретных функций или возможность входа с паролем через token.php.
3. [Документация Moodle](https://docs.moodle.org/dev/Creating_a_web_service_client) описывает запросы с токеном и функцией; доступ зависит от конфигурации конкретного сайта. Новые возможности REST/OAuth из других версий нельзя автоматически приписывать установленному порталу: его версия не проверена.

Собственный аккаунт позволяет исследовать доступные пользователю страницы. После отдельного входа самим пользователем можно проверить его курсы, задания, оценки и сетевые запросы. Пароль не следует присылать в чат. SSO подтверждает личность, но сам по себе не открывает данные личного кабинета API-клиенту. Оценки Moodle и MyGRSU могут находиться в разных системах.

Предпочтителен действующий разрешённый сервис с пользовательским токеном. Автоматизация авторизованного чтения страниц технически возможна, но пока не проверена: нужно выяснить формат данных, права, условия использования и восстановление сессии. Нельзя обещать универсальную интеграцию для всех студентов по одному успешному входу. Для массового приложения нужны предсказуемая авторизация, изоляция пользователей и отзыв доступа.

## Что исправить в макетах и спецификации до разработки

- Расписание: поддержать семь дней; реальные интервалы, выбор подгрупп, одновременные события, отсутствие аудитории/типа, длинную комиссию, ошибку загрузки и неопубликованный период.
- Сегодня: вместо безусловного «свободно» использовать «нет занятий по загруженному расписанию» там, где полнота неизвестна. Учебную неделю вычислять только по известному календарю; её номер не получен из проверенных ответов.
- Задачи: явно личные, пока Moodle не подключён. Счётчик «3 сегодня и завтра» в новом макете не согласован со списком: там только два таких срока. Нужны реальные вычисления, а не независимые демонстрационные цифры.
- Ассистент: показать источник, актуальность и карточку подтверждения добавления задач. Оценка «45 минут» и план отчёта — предложение, а не сведения преподавателя. Текст «использует только этот контекст» пока не подтверждён реализацией.
- Карточка пары: материалы показывать только при загруженном файле или подтверждённой связи с курсом; одинаковое название предмета не доказывает соответствие Moodle-курсу.
- Закрытые разделы: до проверки аккаунта показывать «интеграция не подключена» / явное демо, а не обещание автоматической синхронизации.
- Сначала реализовывать ядро с подтверждёнными источниками. Закрытые модули не входят в обещание полностью рабочего продукта до отдельной проверки чтения с аккаунтом.

Критерий допуска интеграции к реализации: успешный запрос с нужными правами; реальные примеры нужных полей; проверенные пустые/ошибочные состояния; известные ограничения охвата; понятное обновление и источник каждого отображаемого факта. Для публичного расписания уже есть реальные примеры, но нагрузка/SLA/полнота не установлены. Для закрытых модулей успешного чтения пока нет.
