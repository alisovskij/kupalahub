# Проверка Moodle API со своим аккаунтом

Публичная проверка 16.11.2026: вход `/login/index.php` перенаправляет на SAML-форму `idp.grsu.by`; `/login/token.php` отвечает JSON `missingparam` без username; REST без токена отвечает `invalidtoken`. Наличие этих обработчиков не доказывает доступность выдачи токена студенту.

Дополнительная проверка после отчёта пользователя `invalidlogin`: публичная функция `tool_mobile_get_public_config` через `/lib/ajax/service-nologin.php` вернула `enablewebservices:1`, `enablemobilewebservice:1`, `typeoflogin:3`, `launchurl:https://edu.grsu.by/admin/tool/mobile/launch.php`. В исходниках Moodle значение 3 означает вход через встроенное окно браузера. Следовательно, веб-сервисы включены, а для подключения приложения настроен браузерный путь входа. Это согласуется с SAML; точная причина отказа прямого пароля остаётся не установлена.

Следующий шаг: после самостоятельного входа на портал проверить «Настройки → Ключи безопасности» (`https://edu.grsu.by/user/managetoken.php`). Доступность этой страницы и выдачи ключа зависит от прав пользователя. При наличии разрешённого ключа Web Services проверить его через вариант 2 CLI. Ключ не отправлять в чат. Если страницы/ключа нет, проверить разрешённый браузерный SSO-процесс; не повторять прямые попытки ввода пароля и не считать API отключённым. Источники: [публичная функция Moodle](https://docs.moodle.org/dev/Web_service_API_functions), [константы видов входа](https://raw.githubusercontent.com/moodle/moodle/MOODLE_405_STABLE/admin/tool/mobile/classes/api.php), [ключи безопасности](https://docs.moodle.org/en/Security_keys).

## Запуск на своём компьютере

```bash
cd /home/artem/python/kupalahub
npm run check:portal
```

Выберите `1`, введите свой логин портала и пароль. Пароль вводится скрыто, не передаётся аргументом команды, не записывается в файл и не печатается. Нужен интерактивный терминал и сеть. Программа обращается только к фиксированному HTTPS-адресу edu.grsu.by; перенаправления запросов с секретами запрещены.

Выберите `2`, если у вас уже есть пользовательский токен Moodle: он также вводится скрыто. Токен и пароль не присылайте в чат. Можно прислать получившийся JSON-отчёт: программа выводит только результат подключения, доступность функций и количества курсов/заданий, без ФИО, ID, материалов и секретов.

Попытка получить токен использует стандартный сервис `moodle_mobile_app`. Он может быть отключён, недоступен данному пользователю либо не принимать пароль SAML напрямую. Не следует многократно повторять вход при ошибке. `invalidlogin` не позволяет однозначно отличить неправильный пароль от несовместимого пути авторизации.

Выдача токена может создать действующий ключ на стороне Moodle. CLI не сохраняет его, но ключ может продолжать действовать на сервере. При необходимости отзовите ключ в настройках портала/через администратора. Сессии браузера CLI не использует и не изменяет.

## Что проверяется

1. Получение токена или использование уже выданного.
2. Чтение `core_webservice_get_site_info`: доступные функции сервиса.
3. Чтение собственных курсов, если разрешено.
4. Чтение перечня заданий максимум десяти собственных курсов, если разрешено: только количества и наличие сроков в отчёте.

Списки участников, оценки и результаты сдачи не скачиваются. Соответствующие capability-флаги означают лишь наличие функции, а не успешное чтение данных. Роль старосты этим не определяется, а участники Moodle-курса не равны официальному составу группы.

Без действительных учётных данных выполнены только публичные запросы и тесты с имитацией ответов. Реальное чтение со студенческим аккаунтом ещё не проверено. Если прямой вход не работает, следующий путь — отдельная проверка SSO/разрешённого токена с администратором; обход защиты не предусмотрен.
