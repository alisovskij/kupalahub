# Kupala Hub: проект веб-приложения

Статус: историческая проектная спецификация. 16.11.2026 пользователь разрешил разработку фронтенда и JavaScript-бэкенда без ИИ. Рабочее ядро реализовано на React/Vite + Fastify + SQLite; актуальные команды и границы версии — в README.md. Предложения ниже о Next.js/PostgreSQL/Redis/ИИ не описывают текущую реализацию.

Уточнение пользователя: текущий этап — только десктопный веб-интерфейс. Мобильные раскладки и проверки 360/768 px, описанные ниже как первоначальный план, отложены. Выбрано направление A «Ясный день» (`design/research/a.html`); дополнительные макеты расписания, задач и ассистента ещё требуют согласования.

Актуальные источники и ограничения: [аудит доступности данных](../../data-feasibility-audit.md). Он уточняет раздел проверки API ниже: непосредственно проверены шесть публичных методов, в расписании найдены события сессии и подгруппы. Закрытые данные MyGRSU и Moodle не входят в подтверждённые интеграции. Наличие REST-обработчика Moodle с ответом `invalidtoken` не подтверждает доступ к данным студента.
Дата: 15 ноября 2026 года.

## Основания и принятые ограничения

- Пользователь хочет воспроизвести приложение из сохранённого макета, улучшив современность и удобство дизайна.
- Разрабатывается только веб-приложение, адаптированное для компьютера, планшета и телефона. PWA — возможности сайта, а не отдельное мобильное приложение.
- Бэкенд и фоновые обработчики пишутся на JavaScript; Python из исходного ТЗ заменяется.
- Пользователь выбрал первую рабочую версию: «Сегодня», расписание, задачи и ассистент; остальные разделы подключаются позже.
- Исходное ТЗ: [читаемая копия](../../reference/requirements.md), [оригинальный DOCX](../../reference/requirements-original.docx).
- Дизайн-референс: [описание и исходники 22 экранов](../../../design/claude-desktop/README.md).
- Все решения ниже, не перечисленные как требования пользователя, — предложения для реализации, а не уже согласованные предпочтения.

## Зачем нужен продукт

Студент должен сразу понимать, какая пара сейчас или следующая, где она проходит, что изменилось и что нужно успеть сделать. Ассистент использует те же данные приложения, показывает источники и помогает выполнить конкретное действие.

Успех первой версии: студент выбирает группу, открывает настоящее расписание, создаёт личную задачу и получает проверяемый ответ ассистента по этому расписанию. Демо остаётся доступным для знакомства и проверки сценариев.

## Подходы к разработке

| Подход | Преимущества | Ограничения |
| --- | --- | --- |
| Next.js для интерфейса + отдельные Fastify API и воркер | Сохраняет клиентский стек ТЗ; явно выделяет JavaScript-бэкенд; API и воркер используют общую бизнес-логику | Требует совместного запуска нескольких процессов |
| Next.js для интерфейса и всего API | Меньше серверных приложений на старте | Фоновый опрос и очереди всё равно требуют отдельного обработчика; сложнее явно разделить интерфейс и серверные модули |
| React/Vite + Fastify | Удобная основа для личного кабинета и SPA | Меняет клиентский стек исходного ТЗ без обязательной продуктовой причины |

Предлагается первый вариант. Один репозиторий, один публичный адрес, модульный сервер. Разделение на микросервисы и отдельный Python-сервис ассистента не требуется.

## Дизайн и удобство

Сохраняем узнаваемость референса: спокойный светлый фон, тёмную карточку текущей пары, зелёный цвет действий и оранжевый акцент времени. Основные изменения — читаемая иерархия, меньше конкурирующих блоков и предсказуемое поведение.

- На первом экране главный ответ — следующая или текущая пара. При отсутствии занятий показываем ближайшее занятие или понятное сообщение о свободном дне.
- Блок ассистента на главной компактный. Полноценный диалог находится в собственном разделе; контекстный запуск доступен из карточки пары.
- Заголовки Unbounded используются выборочно; обычные заголовки и текст — Onest. Моноширинный шрифт оставляем для времени и чисел.
- Максимальная ширина содержимого ограничена; широкие экраны не растягивают строки и карточки бесконечно.
- Единые интервалы на основе 4/8 px, радиусы и высоты контролов; никаких новых вариантов карточек для каждого экрана.
- Тип занятия обозначается подписью и цветом. Изменения имеют текст «было → стало».
- Обязательны состояния загрузки, отсутствия занятий, ошибки, отсутствия сети, устаревших данных и не настроенного ассистента.
- Светлая и тёмная темы используют семантические токены; начальное значение берётся из настроек системы.
- Клавиатурная навигация, видимый фокус, контраст AA, подписанные поля, зоны нажатия от 44 px, reduced-motion.

| Раздел | Поведение |
| --- | --- |
| Первый запуск | Выбор формы обучения, факультета, курса, группы и подгруппы; отдельный вход в демо; повторный запуск сохраняет выбор; собственная регистрация по email для личных задач |
| Сегодня | Сейчас/далее, начало и окончание пары, аудитория, корпус, список дня, окна, ближайшие дедлайны, известные изменения |
| Расписание | День и неделя, переход к текущей дате, фильтр подгруппы, карточка пары с преподавателем и адресом; текущая и следующая неделя офлайн; разовая загрузка ICS |
| Задачи | Создание, редактирование, выполнение и удаление; срок, приоритет, предмет и необязательная привязка к паре; сохранение на сервере |
| Ассистент | Ответы по расписанию, изменениям и своим задачам, ссылки на данные, предложение задачи с подтверждением; потоковый ответ и отмена запроса |
| Минимальные настройки | Группа, подгруппа, тема, режим источника данных; выход и удаление аккаунта с личными данными |
| Изменения | Сравнение снимков и отображение внутри приложения; базовые уведомления внутри интерфейса |

Онбординг и настройки — вспомогательные экраны четырёх основных разделов. Отдельные страницы преподавателей, аудиторий, успеваемости и материалов в навигацию первой версии не добавляются. При упоминании этих возможностей интерфейс объясняет доступность, а не показывает неработающие действия.

Время: реальный режим использует текущую дату и Europe/Minsk. Демо получает фиксированное effectiveNow, одинаковое для экрана и ассистента; сдвиг времени действует только в демо. Пара считается текущей в полуинтервале [начало, конец). Не показываем фиксированные «34 минуты» из референса.

Оценка времени между корпусами показывается только при наличии проверенного справочника; при его отсутствии остаются адрес и внешняя ссылка на карту. Фильтр подгруппы сохраняет общие занятия. Неизвестная подгруппа не исключает занятие молча.

### Отложено до следующих этапов

Web Push, календарная подписка ICS, месяц и печать расписания, отдельный справочник преподавателей, свободные аудитории и полный кампус; затем успеваемость, материалы, сессия, RAG и тесты; позже новости, финансы и группа/староста.

Повторяющиеся задачи, заметки и вложения — расширение планировщика после базового CRUD. Первая версия — на русском; строки вынесены для последующего добавления белорусского и английского. Три языка входят в целевой продукт, а не в первую приёмку.

Нативные приложения, Telegram-бот, распознавание лиц, проведение платежей и запись данных в системы университета в эту разработку не входят. Telegram Login не нужен для первой версии.

## Архитектура и данные

```text
Браузер → единый адрес → Next.js (страницы и ресурсы)
                     → /api/* → Fastify → провайдеры → API ГрГУ
                                         ├ PostgreSQL
                                         ├ Redis
                                         └ адаптер модели
                               BullMQ worker → опрос и снимки
```

Браузер не обращается напрямую к ГрГУ или модели. Бизнес-правила находятся в JavaScript-модулях сервера, используемых API и воркером. Next.js не дублирует бизнес-API через Server Actions.

Основные сущности: Account, StudentProfile, DemoProfile, Session, EducationDepartment, Faculty, Group, Teacher, Lesson, ScheduleSnapshot, ScheduleChange, Task, AssistantConversation и PendingAction. Идентификаторы ГрГУ сохраняются как строки. Нормализованная пара содержит дату, начало/конец, дисциплину, тип, подгруппу, преподавателя, корпус/адрес и аудиторию.

Любой ответ провайдера включает source (grsu/demo), fetchedAt, stale и сведения о покрытии периода. Демо и живые данные не подменяют друг друга незаметно. Ошибка API не создаёт выдуманную пару. Если снимок отсутствует, показывается ошибка с повтором; переход в демо — явное действие пользователя.

Провайдеры: GrsuProvider и DemoProvider с одним контрактом. Учебные закрытые данные впоследствии получают отдельные провайдеры; оценки не вычисляются из публичного логина студента.

## Аккаунт и защита задач

Публичное расписание и демо доступны без регистрации. Для постоянного сохранения личных задач используется собственный аккаунт по email и паролю, как допускает исходное ТЗ. Пароли хешируются Argon2id; доступны регистрация, вход, выход и удаление аккаунта. В интерфейсе сохраняется черновик задачи, если для её сохранения потребовался вход. Данные принадлежат внутреннему accountId, а не email, номеру группы или публичному studentId ГрГУ.

Идентификатор владельца всегда берётся из серверной сессии, в том числе для инструментов ассистента. Непрозрачный случайный токен сессии передаётся через HttpOnly cookie с SameSite и Secure в HTTPS; на сервере хранится его хеш. Срок сессии — 30 суток с обновлением при активности, выход отзывает сессию. Запись защищается проверкой Origin/CSRF, входные данные валидируются, попытки входа ограничиваются. Истечение сессии не удаляет задачи аккаунта.

Демо использует отдельный изолированный профиль на браузер; его действия никогда не изменяют реальные задачи. Проверка email и восстановление пароля через одноразовые ссылки обязательны до публичного запуска с реальными пользователями; выбор почтового провайдера и его конфигурация остаются задачей подготовки размещения. Локальная приёмка может использовать тестовый почтовый транспорт. Приложение не запрашивает пароль портала ГрГУ.

## Кэш, изменения и офлайн

- Кэш ключуется сущностью, периодом и языком, а не отдельным студентом; TTL расписания — 15 минут. Одновременные одинаковые запросы объединяются.
- Общий ограничитель всех исходящих вызовов ГрГУ — не более 2 запросов в секунду, включая API, воркер и повторные попытки. Одна задача BullMQ не обязательно равна одному HTTP-запросу.
- Опрос активных групп: раз в 30 минут 07:00–22:00 и раз в 2 часа ночью по Europe/Minsk. Обещание «изменения за 30 минут» действует для дневного опроса, а не круглосуточно; это уточнение противоречия в исходном ТЗ.
- Снимки хранятся в PostgreSQL; сравниваются нормализованные поля, а не сырой JSON и порядок ключей. Начальный снимок не порождает уведомления о добавлении всех пар. Неопределимые соответствия отображаются как удаление/добавление.
- При сбое API берётся последний снимок с датой; частичная/ошибочная загрузка не заменяет полный снимок и не порождает массовые отмены.
- HTML-парсер резервного сайта не реализуется до проверки формата и необходимости; последнее успешное расписание — первая защита от недоступности API.
- Service worker сохраняет оболочку приложения. Расписание текущей и следующей недели хранится в IndexedDB с датой обновления и метаданными источника. Закрытые ответы и SSE не попадают в общий HTTP-кэш.
- Задачи читаются из персонального локального кэша. Офлайн-запись задач откладывается: интерфейс явно запрещает сохранение без сети и сохраняет черновик формы. Очередь синхронизации и разрешение конфликтов добавляются позже.
- Выход или удаление аккаунта очищает персональные данные IndexedDB и клиентский кэш. Первая версия не обещает офлайн-ответы модели.

## Ассистент

Модель подключается через серверные настройки base URL, model и secret API key. Конкретного провайдера и модель пользователь пока не выбрал; совместимость с tool calling и доступность проверяются перед живой приёмкой. Секреты не включаются в клиент или репозиторий. Без настроек отображается «Ассистент пока не подключён», а не имитация ответа модели.

Инструменты первой версии: get_now_next, get_schedule, get_schedule_changes, list_tasks и propose_task. Все используют те же сервисы и провайдеры, что экраны. Максимум 6 вызовов инструментов за ход, таймаут и ограничение размера ответа. Данные и тексты пользователя не могут менять права или системные инструкции.

Ответы о фактах содержат ссылки на конкретную пару, снимок или задачу. По устаревшим данным предупреждение сохраняется и в ответе. Вопрос о стипендии или оценках получает объяснение отсутствия источника; наличие демонстрационной записи не превращается в реальный факт.

Предложение задачи сохраняется как PendingAction, привязанное к сессии и проверенным параметрам, с временем жизни 10 минут. Запись происходит отдельным защищённым HTTP-запросом после нажатия «Создать задачу». Подтверждение одноразовое, с идемпотентным результатом. Повторный запрос или воспроизведение SSE не создаёт дубликат. Модель не получает инструмент самостоятельной записи.

История диалога в первой версии хранится на сервере только после явного согласия; иначе передаётся текущий контекст разговора без сохранения, с ограничением объёма. Логи не содержат тексты задач и диалогов. Счётчики лимитов и затрат хранят метаданные.

## Проверка API: что известно сейчас

15 ноября 2026 года через браузер успешно получен JSON от https://api.grsu.by/1.x/app1/getFaculties: массив items с id и title. Это подтверждает только этот конкретный публичный метод.

До привязки реального расписания необходимо проверить getDepartments, параметры getGroups, getGroupSchedule с groupId, даты и поля подгрупп. Справочник преподавателей и getTeacherSchedule проверяются перед соответствующим этапом. getStudent не вызывается без предоставленного пользователем логина; этот путь онбординга отложен, пока не нужна привязка по логину.

Проверка строится на публичных справочниках и тестовой группе, без перечисления персональных логинов. Успешные обезличенные ответы фиксируются как контрактные примеры. Неподтверждённые методы не объявляются работающими; при ошибках метод исследуется до разработки зависящего от него сценария.

## Критерии приёмки первой версии

1. Группа выбирается из подтверждённых справочников и сохраняется; демо доступно отдельным действием.
2. «Сегодня», расписание и ассистент одинаково определяют текущую/следующую пару, в том числе на границе времени, в выходной и при разных подгруппах.
3. Запрошенное расписание приходит через сервер с метаданными источника. Сбой ГрГУ показывает последний снимок с датой, а не демонстрационные занятия.
4. Текущая и следующая неделя после загрузки доступны офлайн. Неполный кэш не выдаётся за полное расписание.
5. Задачи сохраняются на сервере и после перезагрузки; после входа доступны с другого устройства. Чужая сессия не может их читать или менять. Удаление требует явного действия и допускает короткую отмену либо подтверждение.
6. Ассистент с настроенной моделью отвечает по данным и источникам; без модели показывает честное состояние недоступности. Предложение задачи требует подтверждения и не создаёт дубликатов.
7. Пустые, ошибочные, офлайн- и демо-состояния проверены на всех четырёх основных экранах.
8. Основные сценарии доступны клавиатурой и на ширинах 360, 768 и 1440 px, без горизонтального переполнения страницы. Сетка недели на телефоне заменяется дневным списком.
9. Проверяются unit/integration-тесты времени, подгрупп, снимков, сессий, владения задачами и подтверждения действий; Playwright проверяет выбор группы → расписание → регистрацию/вход → задачу → перезагрузку, выход, демо и офлайн.
10. Целевые LCP ≤ 2,5 с и Lighthouse Accessibility ≥ 90 измеряются на согласованном профиле, а не заявляются заранее. Для ассистента используется набор вопросов по возможностям первой версии; цели ≥ 90% верных ответов и ≤ 2% выдуманных фактов проверяются отдельно с выбранной моделью.

## Порядок реализации после согласования

1. Проверить контракты необходимых методов ГрГУ и зафиксировать примеры.
2. Собрать дизайн-систему и оболочку, демо-провайдер, адаптивную главную и расписание.
3. Подключить Fastify, собственный аккаунт, PostgreSQL, настоящие данные, задачи и снимки.
4. Подключить офлайн-кэш, обработчик обновлений и список изменений.
5. Подключить адаптер модели, инструменты, источники, потоковый ответ и подтверждение задачи.
6. Пройти приёмку ядра; затем расширять приложение следующими разделами референса.

Это последовательность работ, не обещание календарных сроков. Детальный план по файлам и проверкам составляется после согласования проекта.
